Vibe Coding 是什么 — 在开始之前

Vibe Coding 不是「让 AI 帮你写代码」那么简单。它是一种人机协作的编程范式： 你提供业务直觉和架构判断，AI 负责把想法转化成可运行的代码。 关键在于——你要知道自己要什么，并能验证 AI 的输出是否正确。

📋 需求/SAD
→
🧠 你的判断
→
🤖 AI 生成代码
→
🔍 你来验证
→
🔄 迭代修正
→
✅ 可运行系统
本文档记录的是构建 FC6+6 TCSS 财务预测系统的真实 Vibe Coding 过程。 每个 Step 都包含：你对 AI 说了什么、AI 输出了什么代码、运行结果如何、出了什么问题、怎么修正的。

本项目技术栈：React 18 + TypeScript + Vite + Tailwind CSS + ECharts（前端）／ Node.js + Express + TypeScript（后端）／PostgreSQL + Prisma ORM（数据库）／ JWT + RBAC（认证权限）／SheetJS（Excel 处理）

后端 API — Express 路由实现

Schema 完成后，让 AI 按模块逐个生成 Express 路由。关键是给 AI 提供足够的业务规则约束。

实现收入数据的 CRUD API。要求：
1. GET /api/revenue?versionId=&bu= — 按版本和BU过滤
2. POST /api/revenue — 新增，需要验证版本未锁定
3. PUT /api/revenue/:id — 修改，LOCKED 版本禁止
4. DELETE /api/revenue/:id — 删除

📄 backend/src/routes/revenue.ts TypeScript 
import { Router } from 'express'
import { prisma } from '../db'
import { authenticate, authorize, checkVersionAccess } from '../middleware/auth'

const router = Router()

// GET /api/revenue?versionId=&bu=
router.get('/', authenticate, async (req, res) => {
  const { versionId, bu } = req.query
  const records = await prisma.revenueRecord.findMany({
    where: {
      versionId: versionId as string,
      ...(bu ? { bu: bu as any } : {})
    },
    orderBy: [{ bu: 'asc' }, { month: 'asc' }]
  })
  res.json(records)
})

// POST /api/revenue
router.post('/',
  authenticate,
  authorize('BUSINESS', 'FINANCE', 'ADMIN'),
  checkVersionAccess,
  async (req, res) => {
    const record = await prisma.revenueRecord.create({ data: req.body })
    res.status(201).json(record)
  }
)

// PUT /api/revenue/:id
router.put('/:id',
  authenticate,
  authorize('BUSINESS', 'FINANCE', 'ADMIN'),
  checkVersionAccess,
  async (req, res) => {
    const record = await prisma.revenueRecord.update({
      where: { id: req.params.id },
      data: req.body
    })
    res.json(record)
  }
)

// DELETE /api/revenue/:id
router.delete('/:id',
  authenticate,
  authorize('BUSINESS', 'FINANCE', 'ADMIN'),
  checkVersionAccess,
  async (req, res) => {
    await prisma.revenueRecord.delete({ where: { id: req.params.id } })
    res.status(204).end()
  }
)

export default router
📄 backend/src/middleware/auth.ts — checkVersionAccess 关键逻辑 TypeScript 
// 检查版本是否已锁定，ADMIN 可绕过
export const checkVersionAccess = async (req, res, next) => {
  const versionId = req.body.versionId || req.params.versionId
  if (!versionId) return next()

  const version = await prisma.forecastVersion.findUnique({
    where: { id: versionId }
  })
  if (version?.status === 'LOCKED' && req.user?.role !== 'ADMIN') {
    return res.status(403).json({
      error: { code: 'VERSION_LOCKED', message: '版本已锁定，禁止修改' }
    })
  }
  next()
}
Vibe Tip：每次只让 AI 实现一个路由文件，不要一次让它写完所有后端代码。 分步骤让你能及时验证，出错也容易定位。

审批流引擎 — 状态机编码

审批流是 FC6+6 最核心的业务逻辑。用状态机思维描述给 AI，让它生成原子化的事务操作。

实现审批流状态机。规则如下：
SUBMIT：DRAFT → SUBMITTED（BUSINESS 角色）
FINANCE_REVIEW：SUBMITTED → FINANCE_REVIEWED（FINANCE 角色）
CEO_APPROVE：FINANCE_REVIEWED → CEO_APPROVED（CEO 角色）
LOCK：CEO_APPROVED → LOCKED（ADMIN 或 CEO）
REJECT：任意状态 → DRAFT（FINANCE 或 CEO）

要求：用数据库事务原子执行（更新版本状态 + 写审批记录 + 写审计日志）， 任何状态不合法时返回 400 错误。
明白，这是基于状态机的审批路由，使用 prisma.$transaction 保证原子性：
📄 backend/src/routes/approvals.ts — 核心状态机 TypeScript 
const TRANSITIONS: Record<string, {
  from: ApprovalStatus[]; to: ApprovalStatus; roles: Role[]
}> = {
  SUBMIT:         { from: ['DRAFT'],             to: 'SUBMITTED',        roles: ['BUSINESS', 'ADMIN'] },
  FINANCE_REVIEW: { from: ['SUBMITTED'],        to: 'FINANCE_REVIEWED',  roles: ['FINANCE', 'ADMIN'] },
  CEO_APPROVE:    { from: ['FINANCE_REVIEWED'], to: 'CEO_APPROVED',      roles: ['CEO', 'ADMIN'] },
  LOCK:           { from: ['CEO_APPROVED'],     to: 'LOCKED',            roles: ['CEO', 'ADMIN'] },
  REJECT:         { from: ['SUBMITTED', 'FINANCE_REVIEWED', 'CEO_APPROVED'],
                    to: 'DRAFT',              roles: ['FINANCE', 'CEO', 'ADMIN'] }
}

// POST /api/approvals/:versionId/action
router.post('/:versionId/action', authenticate, async (req, res) => {
  const { action, comment } = req.body
  const { versionId } = req.params
  const userRole = req.user!.role

  const transition = TRANSITIONS[action]
  if (!transition) return res.status(400).json({ error: '未知操作' })
  if (!transition.roles.includes(userRole))
    return res.status(403).json({ error: '角色无权执行此操作' })

  const version = await prisma.forecastVersion.findUniqueOrThrow({
    where: { id: versionId }
  })
  if (!transition.from.includes(version.status))
    return res.status(400).json({ error: `当前状态 ${version.status} 不允许执行 ${action}` })

  // 原子事务：更新状态 + 写审批记录 + 写审计日志
  const [updated] = await prisma.$transaction([
    prisma.forecastVersion.update({
      where: { id: versionId },
      data: {
        status: transition.to,
        ...(transition.to === 'LOCKED' ? { lockedAt: new Date() } : {})
      }
    }),
    prisma.approvalRecord.create({
      data: { versionId, approverId: req.user!.id, action, comment }
    }),
    prisma.auditLog.create({
      data: {
        userId: req.user!.id, action: `APPROVAL_${action}`,
        entity: 'ForecastVersion', entityId: versionId,
        oldValue: { status: version.status },
        newValue: { status: transition.to }
      }
    })
  ])
  res.json(updated)
})

  Array.from({ length: 12 }, (_, i) => ({
    id: `rev-${bu}-${i+1}`,
    versionId: 'demo-v1',
    bu,
    productLine: '主要产品线',
    month: i + 1,
    dataType: i < 6 ? 'YTD' : 'FC',
    baseVolume: 10000,
    growthVolume: i >= 6 ? 500 : 0,
    price: 280,
    amount: Math.round(BASE[bu] * (0.8 + Math.random() * 0.4)),
    grossMargin: 0.58 + Math.random() * 0.1,
    dso: 45 + Math.floor(Math.random() * 20)
  }))
)

export function getMockSummary(versionId: string) {
  const byBU = BUS.map(bu => {
    const records = MOCK_REVENUE.filter(r => r.versionId === versionId && r.bu === bu)
    const revenue = records.reduce((s, r) => s + r.amount, 0)
    const grossProfit = Math.round(revenue * 0.58)
    const expense = Math.round(revenue * 0.35)
    return { bu, buLabel: BU_LABELS[bu], revenue, grossProfit, expense, ebit: grossProfit - expense }
  })
  return {
    byBU,
    totalRevenue: byBU.reduce((s, b) => s + b.revenue, 0),
    totalEBIT:    byBU.reduce((s, b) => s + b.ebit, 0),
    totalFTE: 328, totalCapex: 1240
  }
}
Mock 层的设计是这个项目最聪明的决策之一。它让系统在任何环境（GitHub Pages、本地、演示）都能运行， 同时保留了接入真实后端的能力——只需改一个环境变量。

部署上线 — GitHub Pages 静态发布

Mock 模式让我们可以把完整的前端系统部署到 GitHub Pages，零运维成本，永久在线。

帮我写 GitHub Actions workflow，在 push 到 main 时自动构建前端（VITE_MOCK_MODE=true） 并部署到 GitHub Pages。同时处理 React Router 在 GitHub Pages 上的 404 问题。
好的，需要两个部分：CI/CD workflow + SPA 路由支持补丁
📄 .github/workflows/deploy-fc6-tcss.yml YAML 
name: Deploy FC6-TCSS to GitHub Pages

on:
  push:
    branches: [main]
    paths: ['fc6-tcss/frontend/**']
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm', cache-dependency-path: 'fc6-tcss/frontend/package-lock.json' }
      - run: npm ci --legacy-peer-deps
        working-directory: fc6-tcss/frontend
      - run: npm run build
        working-directory: fc6-tcss/frontend
        env:
          VITE_MOCK_MODE: 'true'       # 关键：启用 Mock 模式
      - uses: actions/upload-pages-artifact@v3
        with: { path: 'fc6-tcss/frontend/dist' }

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: github-pages, url: '${{ steps.deployment.outputs.page_url }}' }
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4

Vibe Coding 经验总结

构建 FC6+6 TCSS 的过程提炼出的 10 条 Vibe Coding 实战原则：

✅ 高效的做法
🎯 一次只让 AI 实现一个文件
📋 把业务规则写进 Prompt（不让 AI 猜）
🔍 收到代码立即运行验证
📌 把错误信息直接粘给 AI
🏗 先定目录结构再写代码
🔄 用统一服务层隔离 mock/real
⚠️ 常见陷阱
❌ 一次让 AI 生成整个系统
❌ 不运行只看代码就信任 AI
❌ 跳过类型定义直接写业务
❌ 让 AI 自己决定数据库设计
❌ 忽略状态机的非法转换
❌ .env 文件忘记加入 .gitignore
⏱ 时间消耗分布（3小时原型）
阶段任务耗时AI 贡献
架构设计目录规划、技术选型20 分钟50%
数据库Schema 设计 + 迁移30 分钟80%
后端 API10 个路由文件60 分钟85%
前端页面11 个页面 + ECharts50 分钟75%
Mock 层mockData + mockApi + service20 分钟90%
部署GitHub Actions + 路由补丁20 分钟80%
最重要的一条：Vibe Coding 的速度来自于你对业务的深度理解，而不是 AI 的能力上限。 你越清楚自己要什么，AI 给出的代码就越准确，迭代次数就越少。 FC6+6 这套系统从零到可演示原型只用了约 3 小时，核心原因是需求文档（SAD）足够清晰。
