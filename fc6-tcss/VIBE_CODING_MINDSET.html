Vibe Coding · 底层思维

任何工作，先问两个问题

在写第一行代码之前，在设计第一张数据表之前，在开任何需求评审会之前——先问自己这两个问题。

这是一种会让人感到不舒服的思维方式。
因为它要求你在还没动手之前，就先回答最难回答的问题：
这件事，值不值得做？做到什么程度才算够？

§1两个必须先回答的问题

不论你在做系统设计、写代码、优化模型，还是开会讨论需求，在正式开始之前，必须先回答这两个问题。否则所有的努力可能方向正确但目标偏离。

Q1
它最终是为了什么业务目的？
不是"功能目的"，不是"技术目的"——是业务目的。这件事不做，公司会怎样？做了，公司会怎样？如果说不出区别，这件事大概率不该做。
Q2
它最终会如何影响财务报表？
落到利润表（P&L）的哪一行？影响收入、毛利、费用，还是资产负债表上的资本？能说清楚落点，才能说清楚做到位的标准。

只有先回答这两个问题，才能做三件事：

回答两个问题之后，才能做到

定义

这件工作的完成标准。 "功能上线"不是完成，"指标改善"也不是完成。完成是：它产生的影响，达到了预设的业务目的。

判断

目前是否已经做到位，还是需要继续优化。 有了财务落点，就有了量化标准——而不是凭感觉说"差不多了"。

决策

这件事本身是否值得做，以及投入是否合理。 如果做到极致，对P&L的影响可以忽略不计，那就不值得继续投入——把资源留给影响更大的事。

§2FC6+6 TCSS 的财务报表落点

以 FC6+6 TCSS 为例，最终目标只有一个：确保公司实现年初制定的净利润目标。 所有模块的设计，都应该能追溯到这个目标在 P&L 上的某一行。

收入（Revenue）
MCL-01 基准收入 + MCL-02 增量收入 — 必须是真实可持续的收入，不能靠压货或不可复现的一次性因素虚高
−
销货成本（COGS）
MCL-04 标准COGS + MCL-05 降本节约 — 降本假设必须有落地依据，不能加入确定性不足的结构性节约
=
毛利润（Gross Profit）
毛利率波动直接触发 KPI 预警（M3）；跨 BU 对比揭示结构问题
−
营销费用（S&M）
MCL-03 — 费用管理的核心战场。维持性费用不能压缩，但增量费用必须有明确 ROI，费用率改进目标必须可执行
研发费用（R&D）
MCL-06 — 未批准项目不计入；计划立项仅进 Rolling 段。防止把"愿望清单"变成 P&L 负担
管理费用（G&A）
MCL-07 — Dead Capital 的主要藏身地。削减计划必须落到具体科目和执行时间，不能停留在"计划削减"
=
EBIT
这才是 FC6+6 TCSS 所有模块汇向的终点。 EBIT率预警触发审批流（M4），版本锁定（LOCKED）意味着这个数字对外承诺

§3实现净利润目标的三个杠杆

年初制定的净利润目标，在执行过程中只有三个真正可以主动拉动的杠杆。FC6+6 TCSS 的每一个功能模块，都应该归属于其中一个。

杠杆 一
收入的可靠性
预测的收入必须是真实可达的，不能依靠：

· 向经销商压货（出货 ≠ 销售）
· 年底囤货计划（Rev_F4）过度乐观
· 尚未签约的"意向订单"

MCL-01 的 MAX(月均, 末月) 设计，本质是要防止用异常高月份拉高全年预测。
杠杆 二
COGS 的准确性
成本预测宁可保守，不能乐观。不能轻易加入确定性不足的降本假设：

· MCL-05 的降本率，必须有合同或 SOP 支撑
· Rev_F17（净节约）的效率提升，必须有 Capex 投入时间线对应
· 自动化项目的月折旧，从投产月起必须计入

过于乐观的 COGS 预测，是年底利润缺口的最常见来源。
杠杆 三
费用的主动管理
当收入和 COGS 基本确定后，费用是唯一可以主动控制的利润杠杆：

· 减少 Dead Capital：长期占用但无产出的资产、项目、人员
· 控制非必要支出：MCL-03 的维持性费用审计，MCL-07 的 G&A 削减计划
· 合理延后费用：研发项目中 PLANNED 状态仅进 Rolling，不进 Firm——把不确定的支出推后，把确定的利润释放出来

§4Dead Capital：最容易忽视的利润漏洞

Dead Capital 是指已经占用了资源（人、钱、时间），但没有产生对应业务价值的部分。它不会在 P&L 上直接亮红灯，却是长期侵蚀利润的主要来源。

🔴
停滞的 Capex 项目
设备已购入，折旧已在跑，但产能没有释放，效率提升没有兑现。Rev_F17 = 净节约 = 效率提升 - 当期新增折旧——如果分子迟迟没有落地，净节约会变成净损失。每延迟一个月，就是一个月的"空折旧"。
🟡
PIPELINE 状态的研发项目
未审批的项目不计入 FC，这是 MCL-06 的设计原则。但现实中，这些项目往往已经有人在花时间推进——人的时间是隐性的 Dead Capital。Rev_F18 的 PIPELINE 计数，是一个用来定期审查"投入但未承诺"项目的信号。
🟡
维持性费用中的"历史惯性"
DCL-11 采集的"必保费用"里，有多少是真的必保，有多少是"一直这么花所以没人质疑"？维持性不等于必要性。 MCL-03 的 Rev_F10 基线，每个季度都应该被重新审视一次。
🟢
可以延后的费用，就延后
不是所有费用都必须在当期发生。合理延后 ≠ 逃避——它是把有限的利润空间分配给最高优先级的投入。 研发项目中 PLANNED → APPROVED 的门槛，正是一道强制延后的过滤器。只有过了这道门，费用才进入 Firm 段、才算正式占用利润。

§5在 Vibe Coding 中运用这个框架

把这两个问题变成开始任何开发任务之前的强制 checklist。不是流程，是思维习惯。

我现在要做什么？
明确具体任务。比如："实现 Rev_F17 的 Capex 折旧按月摊销"。
这个功能，最终的业务目的是什么？
让 MCL-05 的降本预测更准确，从而让 EBIT 预测不因为"少算折旧"而虚高——防止年底利润缺口。
它落在财务报表的哪一行？
COGS 下面的制造费用（折旧），以及 MCL-05 净节约行 → 影响毛利率 → 影响 EBIT。
完成标准是什么？
不是"代码写完了"。而是：任意一个 Capex 项目，输入 totalCapex/depMonths/startMonth 后，7-12月每月的折旧计算结果与手工 Excel 一致，误差 < 1元。
这件事值不值得做？投入是否合理？
在测试数据中，一个500万 Capex 项目如果折旧算错一个月，会导致 EBIT 偏差约 8.3万。对于一家年收入数十亿的公司，这个精度要求是合理的。这件事值得做，而且要做到精确。

给 AI 的 Prompt 也要从业务目的出发

❌ 弱

"帮我实现 Capex 折旧计算，按月摊销"

✅ 强

"实现 Rev_F17 净节约按月计算。业务规则：Capex 从 startMonth 开始折旧，之前月份折旧为0；效率节约同理从 startMonth 开始生效；净节约 = 效率节约 - 月折旧，且净节约不得为负（延迟不能让节约变成损耗）。输出 7-12月数组，每月包含 saving、depreciation、net 三个字段。精度要求：与手工Excel误差 < 1元。"

业务目的（防止EBIT虚高）→ 完成标准（精度要求）→ 边界条件（净节约不为负）都在 Prompt 里，AI 第一次输出就基本能用。

为什么这种思维方式会让人"不舒服"？

因为它要求你在开始之前，就对结果负责。

大多数时候，技术人员更愿意先做再说——先把功能实现，再看效果。但对于一个要支撑财务决策的系统来说，"先做再说"的代价，是整个预测体系都建立在一个方向不确定的地基上。

FC6+6 TCSS 的19条 Rev_F 公式，每一条背后都有一个具体的业务问题：这笔收入是真实的吗？这笔成本计进去是合理的吗？这笔费用非现在花不可吗？

先回答这些问题，再动手编码——这不是多一道程序，这才是 Vibe Coding 真正的工作方式：用代码去实现一个已经想清楚的业务判断，而不是用代码去探索一个还没想清楚的业务问题。
